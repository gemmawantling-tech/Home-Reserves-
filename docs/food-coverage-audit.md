# Food coverage audit — 2026-10-23, before calculator changes

Audited deployed commit 4f9bcfb, food-coverage.js (perUnit, analyse, assess), stock-batches.js, scanning.js, inventory-core.js, product-lookup.js. No household records are present in this repository: app.js stores them in localStorage `home_reserves_inventory_v1`. There is no Firebase integration or authenticated household data endpoint. We cannot reproduce or assert the exact private 2.67-day numerator remotely. The new on-device calculation details will run the old algorithm against actual local state, without transmission.

Old result = sum(perUnit(product) × usable recorded quantity) / (householdKcal override, otherwise people × 2,000). A rounded 2.67 at 8,000 kcal/day corresponds to approximately 21,360 kcal, not proof of the exact private numerator.

Included: categories typed food; nonalcoholic Drinks / beverages. Excluded: water, alcohol, nonfood, no/zero/invalid stock count, batches past a recorded date. Unknown dates are included. Batches are reconciled to the recorded count. Each row is counted once, independently of recipe links or portions.

Per-unit priority: explicit kcalPerUnit; otherwise per-100 label kcal (or kJ/4.184) × metric pack size / 100; otherwise per-serving kcal × pack size / parseable compatible serving size. Loose kg/g/l/ml override pack size to avoid multiplying twice. Serving-only data with no pack size is discarded, even if a serving count is known. Unknown weights, missing nutrition, incompatible serving dimensions are null and contribute zero to the old energy numerator. Portions are not meals and are not used for energy. Whole-unit overrides can become stale after stock-unit or pack-size edits. There is no confirmation of edible/drained basis, prepared-vs-dry consistency, or source reliability; the algorithm assumes ordinary label fields apply to stock as sold. Prepared-only nutrition is ignored. A source reporting prepared calories in ordinary per-100 fields could therefore be incorrectly accepted. Household default treats children and adults alike until an override is entered.

Barcode audit: rear camera ZXing EAN13/EAN8/UPCA; no UPCE. Check digits enforced. UPC-A canonicalised to leading-zero EAN13, but saved local records compared by literal strings: UPC aliases can miss catalogue/inventory or duplicate records. Open Food Facts is the sole provider; normalisation rejects multipack labels; a successfully read code absent from OFF is not a camera failure. Community database coverage cannot be guaranteed or corrected by switching camera libraries. No licensed secondary food provider/API credential is configured. Do not introduce scraping or undisclosed nutrition guesses. Add canonical local matching, UPC variants/UPC-E expansion, transparent not-found/error messages and reusable household manual entries; retain a separate provider interface.

Implementation plan: retain old analyse for local legacy diagnostics; add independently tested conservative verified/estimated/unassessed ledger, explicit nutrition/edible basis and source confirmation, serving-count arithmetic, per-member requirements and explicit manual estimates with required source/confidence. Never extrapolate unknown stock or nutrition. Show excluded records as unassessed, with direct corrections and recorded totals, rather than presenting incomplete energy as the whole cupboard. No stock or schema-reset migration.

## Implemented result

`energy-assessment.js` is a separate pure ledger. Old `FoodCoverage.analyse` is retained only for diagnostic/backwards accounting; the dashboard uses the new ledger. Complete legacy/imported label records are provisional estimates until label, quantity, edible amount and matching basis are confirmed. Missing records remain visibly unassessed. Estimates require explicit opt-in, kcal per counted unit, source, assumptions and low/medium confidence; no default generic nutrition table is injected. Verified and provisional energy are disjoint; estimated coverage includes both, not a second amount to add to verified days.

The member editor saves one editable requirement per person. Existing household targets and size remain the fallback until reviewed; mismatched member count falls back visibly. Saving a household-size/override change clears stale member requirements. Child/adult starting values are illustrative editable planning defaults, not age-specific clinical recommendations.

Pack/label edits invalidate the verification signature automatically. Serving-count energy can work without weight only when that method is selected explicitly; known serving sizes cannot imply more edible contents than the recorded pack. Loose mass/volume uses its native unit once. Whole-unit overrides remain explicit and take priority in auto mode; UI warns to clear stale ones. Sources, confidence, assumptions, dated/undated quantities and per-row arithmetic appear in Calculation details. Confirmed no-cook meal portions require explicit complete-meal and preparation flags and are independent of nutrient completeness; unknown preparation is reported separately. Different IDs with duplicate barcodes are flagged for review, not destructively merged or assumed to represent the same physical stock. Duplicate IDs never inflate the new ledger.

Barcode changes add EAN/UPC canonical local matching (including legacy UPC-A records), explicit camera UPC-E expansion, UPC/EAN lookup alternatives and unambiguous multipack sizing. Manual product corrections are reused without another external lookup. Not-found responses differ from camera permission/invalid-checksum/network errors. The existing ScanGate and transaction tokens prevent repeated camera frames and save retries inflating quantity. A licensed-provider registration boundary is available, but no second provider is enabled: no compatible credentialed food service is configured, and this static app must not expose private API keys. Product availability across supermarkets is still limited by the external database. There is no claim of a measured improvement in the user's recognition rate without representative scans.

## Validation and limits

Synthetic tests include 40 × 250g rice, tins of beans, dry pasta/rice, liquids and loose mass, differing serving sizes, prepared/drained bases, missing fields, no-cook meals and a two-adult/two-child 7,400 kcal planning example. A deliberately constructed 21,360/8,000 = 2.67 fixture validates the legacy diagnostic; it is not asserted to be the private household inventory. Browser tests use isolated synthetic localStorage, verify sources/estimates/member targets across reload, barcode alias handling, repeated detections, remembered manual products, metadata preservation and backup recovery. Actual household data can be audited only on the user's device or from a voluntarily supplied backup; none is accessed or transmitted by the diagnostic.
